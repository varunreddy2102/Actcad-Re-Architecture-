Chapter 01

Why now

Three forces are converging on the CAD market in the next 24–36 months. The current stack is structurally blocked from meeting any of them.

Why now — three forces converging

⚡

Force 1

AI is table stakes

Autodesk shipped MCP servers in Revit 2027 and Fusion 2026. Graebert shipped A3 agent. BricsCAD shipped AI Assistant. We are structurally blocked — IntelliCAD's consortium license forbids operating AI on the foundational codebase.

☁

Force 2

Cloud + web are baseline

AutoCAD Web since 2018. Onshape cloud-native from founding. ARES Kudo ships a browser DWG editor. Snaptrude is cloud-native AEC. We are Windows-only because of how IntelliCAD's shell is structured.

▣

Force 3

BIM is moving downmarket

SMB AEC customers in India / SEA / EU increasingly ask for IFC import / export and lightweight BIM. Adding this on top of IntelliCAD is a renderer-tuning treadmill we don't win.

If we are not on the new architecture by year 3, we will be selling against products that are. — Re-architecture plan, §0
These three forces are independent but compounding. The AI block is the most acute today. The web gap is the most visible to customers. The BIM downmarket is the slowest-moving but the most consequential for our segment positioning over 5 years.

Chapter 02

The plan

Replace the engine in three phases, keep the existing product shipping through phase two, and own every layer of the new stack ourselves.

The strategic bet

Replace IntelliCAD with a first-party engine on four foundations:

ODA SDKs · directThe same foundation Bricsys, GstarCAD, ZWCAD, NanoCAD build on
ACIS (Spatial / Dassault)Same kernel ActCAD uses today via IntelliCAD — AutoCAD ASM is an ACIS fork, lossless DWG round-trip
C++ · Qt 6 native · WASM browserMaya / Houdini / AutoCAD-Web pattern
AI-native from day oneMCP server in the engine · transactional undo

Four differentiators we commit to publicly

1

Drop IntelliCAD — go ODA-direct

Same foundation BricsCAD ships on. Removes the consortium release-cadence trap: we no longer wait for shared upstream fixes, we own every release.

2

Real-time multi-user editing on a shared DWG

Two designers edit the same drawing live — like Google Docs for CAD. Server validates geometry edits; comments and properties sync instantly. ARES Kudo hits this wall with soft-locking; we don't.

3

AI inside the drawing, with one-click undo

Every AI action — drafted, edited, or generated — lands in the host as a single undoable transaction. No competitor has documented this publicly; users get AI help without losing Ctrl+Z.

4

Plugins that run on desktop and web

One plugin developer reaches both the desktop product (BRX / .NET-style) and the browser product (Onshape-style). One marketplace, one revenue share.

The four differentiators are deliberately scoped to things competitors have not yet committed to publicly. We can ship to market with these as headline claims and back each one with shipping code.

The two architectural guarantees in this diagram: (1) only db mutates state, so the op-stream is the single source of truth for replication, undo, and agent context; (2) only cmd is the agent seam, which is what makes "every MCP tool call = one undo transaction" enforceable as a property of the architecture, not as a discipline.

Memory architecture — designing for headroom from day 1

CAD model: open the drawing once, hold it entirely in memory, edit there, write back on save. Correct and unchanged. Bottleneck risk lives in how we manage that memory. Five layers, one rule, eight commitments — strategic picture in docs/rearchitecture-plan.md §16; full engineering reference in docs/memory-architecture.md (~900 lines: concurrency model, KAL contract, eviction protocol, failure modes, CI gates, anti-patterns).

Five memory layers

LayerWhat it holdsEvictable?
1. db — DWG databaseEntities, handles, layers, blocksNever — single source of truth
2. ACIS bodies — kernel graphENTITY graph per touched solidLazy — load on first touch
3. Tessellation — GPU trianglesRender-ready buffersYes — LRU evict
4. Spatial indexesR-tree / BVH for hit-test / snapRebuildable
5. Undo / op-logDelta records (also feeds sync + agent + audit)Truncatable

Eight commitments that keep responsiveness flat

  • Single-mutator db + MVCC reads — no reader ever waits on a writer
  • Spatial index built at load time — no linear scans, ever
  • Lazy ACIS materialization — kernel graphs paid for only when a solid is touched
  • GPU-resident evictable tessellation — LRU evict under memory pressure, regenerate on demand
  • Delta-not-snapshot undo — same op-stream feeds sync + agent + audit
  • Declared memory budget per drawing — sized to the target machine class
  • Fail loudly, never silently swap to disk — out-of-budget drawings get a clear error, not a frozen UI
  • 8 ms UI-thread budget — enforced by debug-build asserts in CI, not by code review discipline
Why this matters strategically: the "moderately large drawings get stuck" reputation is the single biggest competitive vulnerability we inherit from IntelliCAD. The memory architecture is the place to fix it for good — at commit 1, with profilers and CI gates wired in from the start, not retrofitted after GA.
The CAD industry consensus is open-once-edit-in-memory-write-on-save — we don't try to be clever and stream entities. What we do change is the discipline around the in-memory structure: single mutator + MVCC readers, lazy ACIS materialization (kernel graphs cost memory only when touched), evictable GPU tessellation, declared memory budgets, and an 8 ms UI-thread budget enforced by CI asserts. Out-of-budget drawings get a clear error; no silent swap-to-disk failure mode of the kind that makes AutoCAD-on-old-hardware look frozen and force-quit-lose-work. The "stuck on moderately large drawings" perception is the single biggest reputational wound we carry forward from IntelliCAD — fixing it at commit 1 is the only honest way to close it.

Why we don't ship web-first

Industry default

Web-first because the future is cloud

  • SaaS-style validation cycles
  • Fastest path to a usable demo
  • Maximum market reach

ActCAD reality

Native Windows first, web in parallel

  • Installed base is Windows desktop SMBs in India / SEA
  • Their hardware has unreliable browser WebGPU
  • Web-only beta would produce zero useful signal
  • Revenue protection requires daily-driver to ship first
The architectural discipline that forces portability (the C ABI, kernel layer, op-stream) is preserved either way. What changes is which shell sees production first.

Phase 1 native Windows daily-driver. Browser ships as viewer + markup in parallel. Full browser editor in Phase 2.

This is the most likely place management will push back ("why not just go web?"). The answer is customer-segment specific: our installed base is on hardware where browser perf is the limiting factor. AutoCAD Web took 7+ years to be a credible editor — we don't have that runway against our installed base's needs.

Why per-deployment for ActCAD

SMB scale, high-volume / low-price product, mix of perpetual + subscription. Per-seat creates a linear-forever liability on every perpetual seat we've ever shipped. Per-deployment is a one-time amortized hit over 5+ year seat lifetimes.

High-price low-volume MCAD (Plasticity / Shapr3D / KeyShot), or pure subscription with 40%+ churn, or single-customer site licenses. Documented for honest comparison only.

AI strategy — three steps, not a chat panel

MCP = Model Context Protocol — the open standard that lets Claude, ChatGPT, or Cursor drive an app's commands like a co-pilot. Autodesk shipped it in Revit 2027 / Fusion 2026; we ship it inside the engine, transactional from day one.

The public commitment no competitor has made

Every MCP tool call resolves to exactly one transaction in the host undo stack.

Revit 2027, Fusion 2026, and ARES A3 all shipped MCP / agent surfaces in 2026 without documenting transactional undo semantics publicly. Making that commitment up front and backing it with architecture is a competitive differentiator that becomes harder to copy the longer they ship without it.

Live multi-user editing — Google-Docs-style, but for DWG

Two designers on the same drawing, in real time. The challenge: a drawing isn't a text document — moving a door has to keep the wall it's attached to. We split the problem in two tiers.

Tier 1 — The drawing itself (geometry)

Server validates every edit before applying

  • Doors stay attached to walls. Dimensions stay attached to entities. Hatches stay inside their boundaries.
  • Each user sees their own edits instantly (optimistic UI); the server quietly checks for conflicts and rolls back the offending one if any.
  • Same edit log feeds undo, sync, AI context, and audit — one source of truth.
  • Presence indicators + click-to-lock for the entity you're holding.
Tier 2 — Annotations, comments, layer properties

Figma-style: last edit wins, instantly synced

  • Comment threads, dimstyle tweaks, layer colors, plot setup — each updates independently, so two users editing different settings never collide.
  • Z-order and draw-order use fractional indexing — the same trick Figma and Notion use.
  • Sheets, layouts, and viewports can't be reparented into cycles (the system rejects the move).

Why this beats today's competition: ARES Kudo (the closest peer) ships a softer "one person edits, others watch + comment" model — when two people want to edit the same drawing they take turns. Onshape solved the same problem with a server-validated edit log; we use the same pattern. The current research path (called "CRDT" — conflict-free replicated data types) runs out of memory on the million-entity drawings typical for MEP risers; we don't go there.

The two-tier model is what gives us both correctness (Tier 1 server-side validation prevents inconsistent drawings) and responsiveness (Tier 2 LWW for everything that doesn't have referential constraints). This is the design Onshape, Figma, and academic geometry-aware CRDT papers have all converged on.

Plugins + marketplace — desktop and web, one catalogue

For customers: more add-ons across more devices. For developers: one plugin, every product surface — desktop, browser, tablet.

What runs where

Desktop plugins (Windows / Mac / Linux)

Compatible with the BricsCAD / AutoCAD plugin ecosystem (BRX-style). Today's customer plugins keep working. Each plugin is digitally signed; "verified publisher" badge in the marketplace.

What runs where

Web + tablet plugins

Same plugin developer, same marketplace listing — extension runs in the browser product (and on iPad / Android tablet later). Sandboxed by the browser, permission-gated like a phone app.

The customer story:

One marketplace · one developer · works on desktop and web · same scope and security on both

Same internal command + query surface under the hood — desktop calls it in-process, web calls it over a secure REST channel. Same audit trail, same permissions, same data.

Marketplace: 15% revenue share above a $5K / year free tier (Apple-style threshold for small developers). Avoids the SolidWorks pattern of demanding revenue share without a real storefront.

No shipping CAD product has true plugin parity across native and web today. We promise API parity (not binary parity) — same RPC contract on both sides. Plugins that need raw geometry-kernel access stay native-only; everything else can ship on both.

What we deliberately don't do

  • No web-first to the installed base. Our customers' hardware can't run a serious browser CAD editor today. Web ships in parallel as viewer + markup, not as the daily driver.
  • No "let the database resolve conflicts automatically" for geometry. The trendy approach (called CRDT — conflict-free replicated data types) runs out of memory on real CAD drawings. We use a server-validated edit log instead, restricting auto-merge to comments and properties only.
  • No SDS / DIESEL / VBA / COM / ADS. Legacy AutoLISP-era extension APIs with shrinking usage. Maintenance cost outweighs customer value.
  • No ObjectARX-compatible .NET surface. Our .NET extension API is opinionated and modern, not bug-compatible with AutoCAD's. We say this up front so partners can plan.
  • No experimental memory-safe languages in the engine hot path. C++20 stays the primary engine language. Rust is used only at the edges (sync, AI agent, scripting host).
  • No alternative kernel. Anything that isn't ACIS introduces translation drift on AutoCAD-origin SAT blobs. The KAL preserves the swap option as an architectural escape valve, but ACIS is the only kernel we ship.
  • No "describe your design to a chatbot and we'll generate it." Hypar's lesson: a 2024–25 BIM-via-chat startup that pivoted in 2025 — text-to-building was the wrong abstraction; they rebuilt around "suggestions in the editor" instead. We start there.
  • No two products forever. Existing IntelliCAD-based ActCAD ships through Phase 2 to protect revenue, then enters published sunset in Phase 3.
Each "don't" closes a door that competitors keep open and pay for.
The boundary-setting is as important as what we commit to. Every "don't" represents a cost we're not paying — whether that's maintenance burden (VBA), brand confusion (two products forever), or a strategic dead-end (Bernini-style chat-CAD).

Migration story for existing customers

Product

IntelliCAD ActCAD ships through Phase 2. Sunset date announced when new product reaches GA, not picked up front. Customers migrate when the new product reaches the feature they need.

LISP scripts

Compatibility shim covers measured customer corpus — 80% percentile in Phase 1, 95% in Phase 2. Migration tool ships in Phase 2 for the long tail.

.NET / IRX extensions

Paid migration service delivered by the same team that built the new APIs. Strategic-customer scripts get hands-on transition support.

File formats

Full DWG round-trip parity from Phase 1, validated against a corpus that includes real customer drawings. No file-format conversation needed.

Pricing: existing perpetual licenses upgrade to new perpetual tier. AI / cloud features are the new subscription line.

The migration story has to be told three times: to existing customers, to the support team, and to sales / marketing. Each audience needs a different level of detail; the principles (revenue protection, no forced upgrade, paid help where it matters) stay the same.
